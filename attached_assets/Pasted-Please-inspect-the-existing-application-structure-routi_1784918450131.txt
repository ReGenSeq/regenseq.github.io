## 2. Instruments

All instruments should inherit from the shared `Instrument` abstract base class.

### Communication protocols

Instrument implementations should use the appropriate communication-protocol mixin, such as:

* Serial
* TCP/IP
* USB
* HTTP
* Vendor SDK
* Simulated or mock communication

The communication layer should remain separate from instrument-specific behavior wherever practical.

### Asynchronous communication

All commands that communicate with physical hardware should be asynchronous.

This includes operations such as:

* Connecting
* Disconnecting
* Sending commands
* Reading responses
* Moving hardware
* Starting or stopping acquisition
* Waiting for hardware state changes

### Naming asynchronous hardware commands

Low-level asynchronous commands that communicate directly with an instrument should use a leading underscore.

Examples:

```python
async def _move_to(self, position: float) -> None:
    ...

async def _set_temperature(self, temperature: float) -> None:
    ...

async def _capture_image(self) -> Image:
    ...
```

Explain that the leading underscore identifies low-level internal hardware operations. Public methods should generally validate the request and add the corresponding operation to the system queue rather than bypassing queue management.

## 4. System queues

Each system should maintain a task queue.

### Queue behavior

System queues must:

* Process tasks in FIFO order by default
* Assign a unique ID to every task
* Support pausing and resuming
* Allow queued tasks to be reordered
* Allow queued tasks to be deleted
* Expose task status clearly

### Task immutability

Once created, a queued task may be:

* Reordered
* Deleted before execution
* Paused as part of the queue
* Inspected

A queued task must not be modified in place.

To change an operation, delete the original task and create a new one. This keeps task history predictable and prevents the parameters displayed to the user from differing from those that are eventually executed.

Add a **Why this matters** callout explaining that immutable tasks improve reproducibility, auditability, debugging, and user trust.

## 5. User interfaces

User interfaces should clearly separate machine-level settings from experiment-level settings.

Whenever possible, users should interact with safe, validated controls rather than editing low-level hardware values directly.

The interface should:

* Validate configuration before execution
* Show clear validation errors
* Display queued and active tasks
* Show task IDs and statuses
* Allow supported queue operations
* Prevent unsupported changes to running or completed tasks
* Make the source of each setting understandable

Experiment and software settings that users need to change easily should be stored in:

These may include:

* Default flow rate

## 9. Contributor checklist

End the page with a concise checklist:

* User-provided inputs are validated through `params`.
* Internal structured data uses `attrs` where appropriate.
* Public APIs include type annotations.
* Instruments inherit from the shared instrument interface.
* Systems inherit from the shared system interface.
* Communication behavior is separated through protocol mixins.
* Direct hardware communication is asynchronous.
* Low-level asynchronous hardware methods use a leading underscore.
* Public system methods create queued tasks.
* Queues are FIFO by default.
* Every task has a unique ID.
* Queued tasks can be reordered or deleted, but not edited.
* Machine-specific values belong in `machine_settings.yaml`.
* User-editable experiment settings belong in `default_config.toml`.
* Reagents are mapped under `[method.reagent]`.
* Fluidics defaults are defined under `[method.fluidics]`.
* Recipes use a simple user-facing YAML format before being validated and expanded.
